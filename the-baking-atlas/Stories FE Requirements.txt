The Baking AtlasStories – Frontend Behavior & RequirementsPurposeDefine how Stories should be surfaced, discovered, and read in the frontend, with a strong emphasis on map-first discovery and long-form reading. This document translates backend story capabilities into clear frontend behaviors.This is an internal product + engineering spec intended to guide future frontend iterations without locking implementation details too early.1. Core UX Principles (Stories)Before features, these principles should guide every UI decision:1. Stories are destinations, not tooltipsThey deserve space, focus, and continuity.2. The map signals depth, not volumeVisual indicators should suggest presence of narrative, not data completeness.3. Discovery feels continuousUsers should never feel like they are "switching modes" between map and stories.2. Story Discovery on the Map2.1 Country / Region IndicatorsRegions that contain one or more stories should be visually distinct from:* regions with no data* regions with only non-story dataRecommended approach:* Use a secondary visual affordance layered on top of existing country highlighting* Examples (choose one, not all):o subtle texture or pattern overlayo slightly deeper saturationo small, non-intrusive glyph (e.g. dot or mark) at region centroidAvoid numeric badges ("3 stories") — this turns depth into a score.2.2 Hover / Focus States (Optional, Non-Blocking)On hover or focus:* Show a lightweight hint such as:o “Stories available”o Story titles preview (max 1–2)This should never block interaction or reading.3. Entry Points to StoriesStories should be accessible via multiple, reinforcing entry points.3.1 Primary Entry: Region Info PanelWhen a user selects a region:The Info Panel should include:* Region name* Brief contextual description (optional)* Stories section (if stories exist)Stories section behavior:* Display a list of story previews:o titleo short summary / excerpto optional time_context labelThis list is the primary gateway to story content.3.2 Secondary Entry: Direct URLsEach story must be accessible via a stable route:* /stories/{slug}Behavior:* If accessed directly, the story view loads without requiring map interaction* The map may be minimized or omitted entirely in this contextStories must stand alone without map dependency.4. Story Reading Experience4.1 LayoutStories should open in a dedicated reading surface:* Can be a full-height side panel, drawer, or page* Must feel distinct from list viewsAvoid:* Modal popups* Small scroll containers nested inside panels4.2 Story Header RequirementsAt minimum, display:* Title* Author name* Time context (historical / modern / etc.)* Associated regions (lightweight, non-clickable initially)Optional:* Summary as an italicized lead-in4.3 Body RenderingThe body field should support:* Headings* Paragraphs* Inline emphasis* Block quotesStrongly recommended:* Render from Markdown* Constrain line length for readabilityAvoid:* Dense UI chrome* Excessive inline links4.4 Sources & TransparencyIf sources is populated:* Render as a collapsed section at the bottom of the story* Label clearly (e.g. “Sources & References”)This reinforces credibility without breaking narrative flow.5. Navigation & Continuity5.1 Returning to ExplorationFrom a story view, users should be able to:* Close or dismiss the story* Return to the previous map context, not a reset stateThe user should feel like they are peeling layers back, not starting over.5.2 Cross-Story Discovery (Deferred)Do not implement yet, but plan for:* Tag-based links (ingredients, techniques, themes)* “Related stories” sectionsThese should be additive, not required.6. Mapping Backend Fields to Frontend UsageBackend FieldFrontend UsagetitleStory header, list previewsslugRouting, URLssummaryPreview text, optional lead-inbodyPrimary contenttime_contextMetadata labelauthor_nameAttributionsourcesCollapsed footer sectionregion_codesMap highlighting, Info Panel groupingtag_namesFuture discovery surfacesextra_dataReserved for future UI enhancements7. Explicit Non-Goals (For Now)* Inline commenting* Likes or reactions* Story ratings* Auto-generated summariesThese features risk pulling attention away from reading.8. Success Criteria (Frontend)The Stories UI is successful if:* Users naturally discover stories while exploring the map* Reading feels uninterrupted and intentional* Stories feel meaningful even when accessed directly* Adding new stories does not require UI redesign9. Design Heuristic (Keep This Close)If a UI decision makes a story feel smaller, faster, or skimmable — reconsider it.Stories are the reason the Atlas exists.End of Stories Frontend Requirements
